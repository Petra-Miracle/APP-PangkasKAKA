Roadmap yang saya sarankan
Fase 0 — Kebersihan env & secrets (sebelum apapun lain)

Repo ini gak punya .env/.env.example sama sekali — selama ini jalan karena Emergent inject env langsung. Begitu pindah host, ini wajib dibikin dulu.
JWT_SECRET harus digenerate baru yang kuat untuk prod (bukan warisan dari environment demo).
MongoDB Atlas cluster baru yang terpisah dari database demo Emergent — jangan bawa data seed demo ke prod.

Fase 1 — Security hardening (cepat, dampak besar, sudah saya temukan sebelumnya)

Tutup /api/seed yang publik tanpa auth
CORS allow_origins=["*"] → persempit ke domain asli setelah hosting fix
Cek rate-limit di /auth/login (belum ada — rawan brute force sebelum ada user asli yang connect)
Pastikan PAYMENT_MODE default di prod bukan simulation
Fase 2 — Pindah hosting dari Emergent

Backend FastAPI → Railway/Render/Fly.io (paling gampang buat solo dev, ada free/murah tier)
MongoDB Atlas
Mobile → butuh EAS Build (belum ada eas.json) + akun Apple Developer & Google Play Console kalau mau submit ke store
bundleIdentifier/package di app.json masih com.emergent.barberbookingai.te8ytx — harus diganti ke identifier milikmu sebelum submit ke store
Webhook Durianpay wajib HTTPS — otomatis kepenuhi begitu ada domain asli
Fase 3 — Payment go-live
Bagian ini sudah didokumentasikan rapi banget di backend/README-payment.md — ada checklist go-live siap pakai. Tinggal dieksekusi: sandbox dulu → test end-to-end nominal kecil → production key.

Fase 4 — CI/CD dasar
History commit sekarang semua auto-commit for <job-id> dari Emergent — belum ada GitHub Actions sama sekali. Minimal: lint + pytest backend + typecheck frontend jalan otomatis tiap push, biar ada "alarm" sebelum bug nyampe ke user asli (walau solo, ini jaring pengaman murah).

Fase 5 — Refactor server.py (2462 baris) → paling terakhir
Saran saya: jangan dikerjain sebelum go-live. Refactor besar di file yang megang semua auth+payment+booking itu berisiko nyuntik bug baru pas belum ada jaring pengaman test yang kuat, di saat kamu justru mau stabil buat user asli. Lebih aman: stabilkan dulu di prod, baru pecah server.py jadi modul (auth.py, bookings.py, payments.py, admin.py, dst) sedikit-sedikit sambil ada test yang jalan.
